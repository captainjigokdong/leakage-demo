# 설계 누수 점검

예측 모델 설계서를 받으면 **데이터 처리나 모델링보다 먼저** 이 점검을 돌리고, 결과를 보고한 뒤에 진행한다.
판정은 규칙 기반 코드가 한다. 너는 결과를 설명하고 수정안을 제안한다. 판정을 직접 바꾸지 않는다.

## 실행 방법

```bash
python scripts/run_check.py <설계서.json> --data <데이터 폴더> [--json 결과.json]
```

- 설계서는 `designs/schema.json` 형식이어야 한다. 형식이 다르면 의미를 바꾸지 말고 그 형식으로 옮긴 뒤 돌린다. 옮길 수 없는 항목은 그대로 보고한다.
- `--data`를 주면 설계서 점검에 더해 데이터의 모든 행으로 다시 확인한다. 데이터가 있으면 항상 준다.
- `leakcheck` 패키지를 못 찾으면 환경 변수 `LEAKCHECK_HOME`을 저장소 루트로 지정한다.
- 종료 코드: 0 = 차단 없음, 1 = 차단 있음, 2 = 점검 불가 (형식 오류, 꼬리표 오류). 2이면 오류 내용을 그대로 보고한다.

## 판정

| 판정 | 뜻 | 너의 행동 |
|---|---|---|
| 차단 | 원리 위반이 확정됨 | 모델링을 진행하지 않는다. 무엇이, 왜 문제인지와 수정안을 보고한다 |
| 경고 | 사람이 판단해야 함 | 진행 전에 사람에게 확인을 요청한다 |
| 통과 | 해당 원리 위반 없음 | 기록만 한다 |
| 기록 | 판정 대상 아님 (Q6) | 그대로 보고에 남긴다 |

## 점검 원리

점검은 사례 목록이 아니라 세 가지 비교로 한다. **규칙표**(`leakcheck/rules.py`)는 각 값이 "언제 알려지는가"만 정한다. 그 값을 쓸 수 있는지는 설계의 예측 시점 tₚ가 정한다.

**시각 비교**
- **Q1 가용 시점** (차단): 모든 특징의 *확인 가능 시각*(값이 생긴 시각이 아니라 알려진 시각)이 tₚ 이전이어야 한다. 창(window)은 그 테이블의 확인 가능 시각 열로 걸러야 상한이 보장된다. 다른 시각 열로 거르면, 두 열 사이 지연의 상한이 규칙표에 있을 때만 보장된다.
- **Q5 선택 시점** (차단): 포함·제외 기준도 특징과 같다. 기준 시점(기본 tₚ)에 이미 알려진 정보로만 누가 들어오는지 정해야 한다.

**단위 비교**
- **Q2 독립 단위** (차단 / 데이터 경고): 분할 키(교차검증 키 포함)는 선언된 독립 단위보다 작으면 안 된다. 위계는 예측 행 < 입원 < 환자 < 가족이다. 독립 단위는 환자보다 작을 수 없다. 데이터에서 선언된 단위보다 큰 묶음이 학습·평가에 나뉘면 경고한다.

**범위 비교**
- **Q3 적합 범위** (차단): 데이터에서 무엇이든 추정하는 단계는 학습 부분에서만 적합해야 한다(`fit_scope`가 train 또는 train_fold). 대치, 척도화, 인코딩, 특징 선택, 리샘플링, 차원 축소, 조정 등이 모두 해당한다. 적합 범위가 적혀 있지 않아도 차단이다.
- **Q4 결과 출처** (차단 / 경고): 결과를 정한 행과 같은 행을 쓰는 특징(같은 테이블이면서 필터·범위·시간 구간이 겹침), 또는 결과 창과 겹치는 창을 쓰는 특징은 차단한다. 같은 테이블이라는 것만으로는 차단하지 않는다. 결과의 대리 변수 목록(규칙표 + 설계서)과 일치하고 결과와 같은 입원 범위의 특징은 경고한다.

**기록·경고만**
- **Q6 다중 시도** (기록): 설계·모델을 몇 번 시도했고 어떻게 보정했는지 남긴다.
- **Q7 결과 확인 균질성** (경고): 결과가 측정으로 정해질 때, 하위 집단마다 측정 빈도가 2배 이상 다르면 결과를 확인하는 강도가 다르다. 설계가 그 층을 따로 다루지(`outcome.ascertainment.by_stratum`) 않으면 경고한다.

**출처 불명**: 특징은 `leakcheck.features.make_feature`로만 만든다. 원본 테이블이 없거나 다른 방법으로 만든 특징은 출처 불명이다. 보고에 "Q1~Q3 확인 불가"로 남긴다.

## 보고 형식

1. 결론 한 줄: 차단 있음/없음, 경고 수
2. 차단과 경고를 하나씩: 질문(Q), 대상(설계서의 항목), 이유, 수정안
3. 통과한 질문 목록과 Q6 기록
4. 점검이 볼 수 없는 것: 규칙표에 없는 출처, 설계서에 없는 결정

점검 결과의 JSON(`question, verdict, target, reason`)을 보고 끝에 그대로 붙인다.

## 진행 규칙

- 차단이 하나라도 있으면 모델을 학습하거나 성능을 계산하지 않는다.
- 차단이 없으면 `--card`로 **결정 카드**(표본 수, 결과율만)를 만들어 사람에게 보여 준다. 사람이 승인해 `leakcheck.lock.DecisionLock`을 잠그기 전에는 성능을 계산하지 않는다. 성능 함수(`leakcheck.lock.auroc`)는 잠금 없이 부르면 예외를 던진다.
- 규칙표, 점검 코드, 판정 기준을 고치거나 우회하지 않는다. 규칙이 틀렸다고 보이면 근거와 함께 보고한다.
- 점검이 통과해도 네가 따로 본 의심점이 있으면 "점검 밖 의견"으로 구분해 보고한다.
