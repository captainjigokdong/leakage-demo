# 채점 규칙 (5단계 고정, 2026-10-03 · 태그 전 수정 같은 날)

`docs/research_plan.md` 7.5를 구체화한 것이다. 실험(6단계) 전에 고정하고, 결과를 본 뒤 바꾸지 않는다.
코드는 `experiment/grader.py`이고, 이 문서와 코드가 다르면 코드가 실제 채점이며 그 차이는 `docs/known_issues.md`에 적는다.
(가)와 (나)에 **같은 규칙**을 적용한다.

## 1. 보고서에서 지적을 꺼내는 방법

- 에이전트 지시문(`experiment/agent_prompt.md`, 두 조건 공통)은 보고서 맨 끝에 `findings` 코드 블록으로
  `[{"target": 설계서 항목 경로, "problem": 문제 설명}, ...]` 목록을 적게 한다. 보고서 언어는 한국어다.
- 채점은 **마지막 `findings` 블록만** 읽는다. 블록 밖 본문은 채점하지 않는다.
  연구 계획의 "애매한 표현은 미탐지"는 여기서 "목록에 넣지 않고 본문에만 쓴 지적은 미탐지"로 정의한다.
  목록에 넣은 지적은 표현의 강도(차단·경고·확인 요청)와 상관없이 지적으로 센다. 그러므로 **경고 수준 지적도 탐지**다.
- 블록이 없거나 JSON이 깨졌으면 그 보고서의 지적은 0개다(형식 오류로 따로 센다). 그 변형의 결함은 미탐지가 되고 오경보는 없다.
- `target`이 문자열 목록이면 각 항목을 따로 지적한 것으로 본다. `target`이나 `problem`이 없는 항목은 버리고 개수만 센다.
- LLM 채점자는 쓰지 않는다. 추출·대조·판정이 모두 규칙 코드다 (CLAUDE.md 절대 규칙 7).

## 2. 지목 항목 (`target` → 설계서 항목)

**채점 대상 항목**: 특징 `features.<name>`, 포함 기준 `cohort.inclusion.<name>`, 제외 기준 `cohort.exclusion.<name>`,
전처리 단계 `preprocessing.<name>`, 분할 설정 `split`, 결과 설정 `outcome(.하위 칸)`, 예측 시점 `tp(.하위 칸)`,
`cohort.subgroups`, `cohort.index_time`.

| 보고서에 적힌 것 | 항목 |
|---|---|
| `features.cr_last`, `features[name=cr_last].time_column`, `features:cr_last`, `cr_last` | `features.cr_last` (하위 칸은 버림, 이름만 적어도 한 목록에만 있으면 인정) |
| `split.key`, `split.method`, `split_unit`, `model.tuning.cv_key` | `split` (**분할 묶음**: 모두 같은 항목) |
| `outcome.aki_48h`(결과 이름), `outcome` | `outcome` |
| `outcome.window`, `outcome.ascertainment` | 그대로 (**결과 묶음**: 아래 대조 규칙 참고) |
| `model.family`, `attempts` | 채점하지 않는 항목 (탐지는 가능, 오경보는 아님) |
| `features`(이름 없음), 없는 이름, 서로 다른 항목 둘 이상, "설계 전체" | **대상 불명**: 탐지도 오경보도 아님, 개수만 셈 |

문자열 전체로 정할 수 없으면 그 안의 영문 토큰을 보되, 점 경로로 적힌 토큰을 먼저 본다.
그래도 항목이 하나로 정해지지 않으면 대상 불명이다.

**정답표 항목과의 대조**
- 특징·기준·전처리·분할: 같은 항목일 때만 일치한다.
- 결과(`outcome.*`)와 예측 시점(`tp.*`): 한쪽 경로가 다른 쪽을 포함하면 일치한다.
  예: 정답이 `outcome.ascertainment`이면 `outcome`, `outcome.aki_48h`, `outcome.ascertainment`는 일치하고, `outcome.window`는 일치하지 않는다.
- **하위 집단 예외**: 정답이 `outcome.ascertainment`(또는 그 하위 칸)이면 `cohort.subgroups` 지적도 일치한다.
  결과를 층별로 확인할지는 하위 집단 설정과 한 묶음이기 때문이다. 그 밖의 정답에서는 `cohort.subgroups` 지적은 별개 항목이다(결함이 아니면 오경보).
- 정답표 항목이 묶음 전체(`cohort`, `model`)이면 그 아래 어느 항목이든 일치한다. `model`은 `split`(교차검증 키)과도 일치한다.

## 3. 문제 종류 (`problem` → Q)

| 종류 | 질문 |
|---|---|
| 시점 | Q1 가용 시점 |
| 분할 | Q2 독립 단위 |
| 적합 범위 | Q3 |
| 결과 출처 | Q4 |
| 선택 | Q5 선택 시점 |
| 확인 균질성 | Q7 |

- 지시문은 이 분류를 에이전트에게 알려 주지 않는다. (나)가 틀을 미리 배우지 않게 하기 위해서다.
- 문제 설명을 **고정된 핵심어 사전**(`grader.KEYWORDS`)과 맞춰 본다. 소문자로 바꾸고 부분 문자열로 찾으며, `tₚ`는 `tp`로 바꾼 뒤 찾는다.
  사전에는 점검기가 쓰는 표현과 일반 표현을 한국어·영어로 넣었다. 예: "미래 정보", "보고 시각", "퇴원 후에 코딩", "예측 시점에 사용할 수 없", "not yet available at prediction" → Q1.
  "같은 환자", "독립성이 깨", "한 사람의 데이터", "both train and test" → Q2.
  "전체 데이터로 적합", "전체 표본에서", "시험 세트 정보", "before splitting" → Q3. "예측하려는 결과", "proxy" → Q4.
  5단계 확인에서 종류 불명으로 떨어진 자연스러운 표현 5개를 보고 보강했다(`tests/test_grader.py::test_keywords_natural_expressions`).
- `Q1`~`Q7` 표기(`Q1~Q3` 같은 범위 포함)도 그 질문으로 본다.
- 한 설명이 여러 종류에 걸릴 수 있다.
- **문맥 규칙 하나**: 지목 항목이 포함·제외 기준(`cohort.*`)이고 시점(Q1)으로 분류되면 선택(Q5)으로도 본다.
  선택 시점은 기준에 적용한 시점 원리이기 때문이다.
- **점검 불가**: "점검 불가", "확인 불가", "규칙표에 없", "출처 불명", "cannot be checked" 등(`grader.UNABLE`)이 들어가면
  다른 핵심어보다 먼저 점검 불가로 분류한다.
  - 탐지도 오경보도 아니며 개수만 따로 보고한다.
  - 그 지적이 결함 항목을 가리켜도 그 결함은 **분모에 남고 미탐지**다.
- 다중 시도(Q6)로만 분류된 지적은 채점하지 않는다(기록만).
- 어느 핵심어에도 걸리지 않으면 **종류 불명**이다.
  - 주 분석에서는 항목만 맞으면 탐지, 보조 분석에서는 미탐지다.
  - 종류 불명 지적 수는 조건별로 따로 보고한다.

## 4. 판정

결함 하나(정답표의 배치 하나)마다 다음과 같이 정한다.

| 판정 | 주 분석 (항목) | 보조 분석 (항목 + 종류) |
|---|---|---|
| 탐지 | 결함 항목을 지목한 지적이 있음 (종류 무관, 종류 불명 포함) | 결함 항목을 지목한 지적 중 하나라도 정답표의 Q로 분류됨 |
| 미탐지 | 그 밖의 경우 (점검 불가로만 지적, 목록 밖 서술, 다른 항목 지적 포함) | 그 밖의 경우 |

- 주 분석과 보조 분석을 바꾼 이유(2026-10-03, 실험 전)는 `docs/success_criteria.md`에 있다.
- **추가 판정**: 결함 항목에 정답 Q 말고 다른 종류가 함께 붙으면 탐지에 영향이 없고 오경보도 아니다. 개수만 기록한다.
- **오경보**: 결함을 심지 않은 채점 대상 항목을 지적한 경우.
  - 깨끗한 변형의 지적과 "수상해 보이지만 정당한" 변경 항목에 대한 지적이 모두 포함된다.
  - 한 보고서 안에서 같은 항목은 한 번만 센다.
  - 종류 불명 지적도 항목이 정해지면 센다.
  - 점검 불가, 다중 시도만, 대상 불명, 채점하지 않는 항목은 세지 않는다.
- 변형에 결함이 둘이면 각각 따로 판정한다.

## 5. 점검기 출력 채점 (2차 지표, (가)만)

- (가) 실행마다 점검기 출력 JSON(`run_check.py --json`, 데이터 포함)을 보고서와 따로 저장한다(6단계 `run.py`).
- 같은 대조 규칙으로 채점하되, 문제 종류는 점검기의 `question` 칸을 그대로 쓴다.
- `차단`과 `경고`만 지적으로 본다. `통과`와 `기록`은 지적이 아니다.
- 다음은 점검 불가로 센다: `question`이 `Q1~Q3`인 것, 이유가 "출처 불명"으로 시작하거나 "확인 불가"를 포함하는 것, 종료 코드 2(전체 점검 불가).
- 이 값은 "점검기만으로 본 탐지율"로 2차 지표에만 쓴다. H1·H2 판정에는 쓰지 않는다.

## 6. 맹검과 절차

1. 6단계 실행기는 보고서를 무의미한 id로 저장한다. 기록에는 `report_id`, `variant`, `text`만 둔다.
   조건(가/나)과 반복 번호는 별도 파일(`conditions.json`)에만 둔다.
2. `grader.py grade`는 보고서·점검기 기록과 정답표만 읽고 조건 파일은 읽지 않는다.
   기록에 조건 칸(`condition`, `arm`, `조건`, `skill`)이 있으면 채점을 멈춘다.
3. `grader.py summarize`가 채점 결과에 조건을 붙여 지표를 낸다.
4. 정답표는 7단계에서 사용자 암호로 메모리에서만 연다. 채점 전에 변형 20개의 SHA-256을 정답표 봉인본·`docs/injection_log.md`와 대조하고, 하나라도 다르면 멈춘다.
5. 한계: 보고서 본문에 스킬 사용 흔적이 남을 수 있어 사람이 읽으면 조건이 드러난다. 채점이 규칙 코드라 이 정보는 판정에 쓰이지 않는다.
